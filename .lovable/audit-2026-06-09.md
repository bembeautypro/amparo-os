> Relatório somente de leitura. Nenhum código foi alterado durante esta auditoria.

## 1. Objetivo do sistema

**Amparo** é um Family Health Hub SaaS mobile-first para coordenação familiar de saúde — pensado para adultos (30-60 anos) que gerenciam a saúde de pais idosos.

Não é app de medicação isolado nem prontuário médico: é uma **central operacional compartilhada** com remédios, agenda, documentos, histórico clínico, contatos de emergência e link público de emergência por paciente.

Princípios do produto (em `mem://index.md` e instruções do projeto):
- Mobile-first sob estresse.
- RLS obrigatório em toda tabela clínica.
- Soft delete (`deleted_at`) — nunca deleção física de dados clínicos.
- Storage privado; uso de `file_path` + signed URLs (nunca URL pública).
- Edge function com `service_role` para acesso público de emergência.

## 6. Autenticação e permissões

### Auth
- **Provider:** Supabase Auth via `@supabase/supabase-js` + Google OAuth via broker `@lovable.dev/cloud-auth-js` (`lovable.auth.signInWithOAuth("google", …)`).
- Sessão persistida em `localStorage` no browser.
- `handle_new_user` cria `profiles` automaticamente após sign-up.

### RLS
RLS habilitado em todas as tabelas listadas. Policies seguem padrão consistente:
- `SELECT` filtra `deleted_at IS NULL` + `app_private.is_family_member(...)`.
- `ALL` (manage) sem filtro de soft-delete (permite restauração).
- `access_logs`: INSERT requer `actor_user_id = auth.uid()`; SELECT por member do family/patient.
- `emergency_links`: INSERT exige `created_by = auth.uid()` + membro; DELETE/UPDATE só membros.
- `families`: creator pode deletar; membros podem `SELECT`/`UPDATE`.
- `family_members`: bootstrap admin pelo creator, join por invitee verificado, ações de admin escopadas.

**Pontos fortes:** uso de `app_private.*` SECURITY DEFINER evita recursão e centraliza autorização.

**Pontos de atenção:**
- Não há policies `TO anon` — toda leitura pública (emergência) **só** acontece via Edge Function com service role, o que é o desejado.
- `patients` tem 4 policies — confirmar que `INSERT` cobre apenas membros ativos.

✅ `No linter issues found`.

## 8. Edge Functions existentes

Apenas uma: **`supabase/functions/log-emergency-access/`**

- Aceita `{ token }`, valida `emergency_links` (ativo + não expirado).
- Carrega em paralelo: paciente (campos sensíveis selecionados), alergias, conditions ativas, contatos, medications ativas.
- Gera signed URL (1h) da foto.
- Registra acesso em `access_logs` (IP, user-agent) e incrementa `access_count` / `last_accessed_at`.
- Retorna JSON consolidado. CORS aberto (`*`) — adequado para página pública.

✅ Bem implementada; segue o princípio "service_role só no servidor".

## 10. Fluxos principais do usuário

1. **Onboarding**
   `register` → `onboarding` (Welcome → Family → Patient → Critical (alergias/condições) → First action) → `dashboard`.

2. **Operação diária**
   `dashboard` resume estado por paciente ativo. Switcher de paciente disponível em todas as páginas (em `AppLayout`).

3. **Medicamentos**
   `medicamentos` → `novo` (com `schedule.times`) → tomadas em `MedicationCard` registram `medication_logs`. Edição gera `medication_change_history`.

4. **Agenda**
   `agenda` lista próximas + concluídas. `novo`/`editar`/detalhe; conclusão marca o appointment.

5. **Documentos**
   Upload (mobile: câmera/galeria; desktop: drag&drop). `file_path` salvo; busca via `search_vector` server-side.

6. **Histórico clínico**
   Eventos com tipo, data, anexos opcionais.

7. **Família e convites**
   `/familia/$familyId/membros` → `InviteDialog` cria `invitations` com expiração (7 dias). Aceitar via `/convite/$token` cria membership.

8. **Emergência**
   Membro gera `emergency_link` (token). Página pública `/emergencia/$token` chama `log-emergency-access` Edge Function e exibe dados críticos + QR.

## 11. Problemas técnicos encontrados

### Arquitetura de rotas
- ❌ **Não usa `_authenticated/`** layout. Em vez disso, há `ProtectedRoute` componentizado. Inconsistente com o padrão TanStack Start recomendado pelo template. Risco: SSR/prerender de rotas protegidas pode ocorrer sem sessão (acrescentado a #12).
- ⚠️ Rotas top-level `/agenda`, `/documentos` duplicam funcionalmente as rotas `/familia/$familyId/...` — possível UX confusa (sempre redirect ou contexto-dependente).

### Metadados
- ⚠️ `__root.tsx` define `og:image` no root — contraria a regra (overrideria leaf images). Bem como `name: "description"` duplicado dentro de `meta`.

### Edge function
- ⚠️ Validação de input fraca: aceita `token` string sem validar formato (regex / length). Recomendado Zod.
- ⚠️ Logging em `access_logs` é best-effort sem retry / observabilidade.

### Banco
- ⚠️ Trigger `handle_new_user` deve ser idempotente (`ON CONFLICT DO NOTHING` já presente ✅) mas não há trigger `update_updated_at` listada nas tabelas — definida a função mas **nenhum trigger ativo** segundo o `<db-triggers>` (sem triggers). Significa que `updated_at` provavelmente não é atualizado automaticamente.
- ⚠️ Soft delete não tem índice parcial (`WHERE deleted_at IS NULL`) — performance pode degradar.

### Frontend
- ⚠️ `AuthContext` chama `supabase.auth.getSession()` (recomendado usar `getUser()` em fluxos sensíveis).
- ⚠️ `useActivePatientForFamily` mantém efeito que pode disparar set em loop se `familyPatients` mudar de referência (filter cria novo array por render). Memorizar com `useMemo` recomendado.
- ⚠️ `FamilyContext`: efeitos de hidratação dependem de `activePatient` no array de deps — risco de loops sutis.
- ⚠️ Não há `errorComponent` / `notFoundComponent` por rota com loader (revisão).

### Segurança operacional
- ✅ Linter Supabase limpo.
- ✅ Buckets privados, signed URLs via hook.
- ⚠️ `EmergencyModal` exibe dados sensíveis — validar se há rate-limit no token.
- ⚠️ `emergency_links` aceita `access_count` ilimitado e tempo de expiração não-imposto via trigger (apenas validado em código).

## 12. Débitos técnicos

1. Sem subtree `_authenticated/` — auth gate disperso em componentes.
2. `__root.tsx` com `og:image` global e meta duplicado.
3. Inexistência de triggers `BEFORE UPDATE … updated_at` ativas.
4. Sem testes automatizados (nenhum diretório de testes).
5. Sem CI/lint pipeline visível além de `eslint`.
6. Múltiplas rotas redundantes (`/agenda`, `/documentos`) sem documentação clara.
7. Edge function única sem validação Zod nem rate-limit.
8. `react-pdf` listado como dependência obrigatória no project-knowledge mas **não instalado** no `package.json`.
9. Não há testes de RLS (queries de smoke por role).
10. Sem indexes parciais para soft-delete; queries verbose com `.is("deleted_at", null)` espalhadas.
11. Mistura de padrão modern (server-fn `account.functions.ts`) com fetch direto do `supabase` no cliente — sem regra clara sobre quando usar cada um.
12. `routeTree.gen.ts` tem sido editado manualmente em migrações anteriores (não recomendado).

## 13. Melhorias recomendadas

### Curto prazo (segurança / correção)
1. **Adicionar triggers `update_updated_at_column`** em todas as tabelas com `updated_at`.
2. **Validar `token` na Edge Function** com Zod (`z.string().uuid()` ou regex de tamanho).
3. **Rate-limit** em `log-emergency-access` (cache de IP, threshold por minuto).
4. **Mover rotas protegidas para `_authenticated/`** seguindo o padrão TanStack Start (gate único, SSR off).
5. **Remover `og:image` do `__root`**, mover para leaves; deduplicar metas.
6. **Instalar `react-pdf`** (declarado nas regras de produto, ausente).

### Médio prazo (DX / performance)
7. Criar **índices parciais**: `CREATE INDEX … ON medications(patient_id) WHERE deleted_at IS NULL;` (idem para appointments, documents, clinical_events).
8. Introduzir **view ou helper SQL** para soft-delete (evitar `.is("deleted_at", null)` espalhado).
9. **Memorizar** filtros em `useActivePatientForFamily` e `FamilyContext`.
10. Substituir `getSession()` por `getUser()` quando a chamada precisa revalidar identidade.
11. Padronizar acesso a dados: server functions (`createServerFn`) para leituras críticas; client supabase para realtime/UI.
12. Cobertura básica de **testes RLS** com `pgTAP` ou smoke tests por role.

### Longo prazo (produto)
13. **Notificações** (push/web) para lembretes de medicação e consultas próximas.
14. **Adesão / aderência**: dashboards melhores em `AdherenceCalendar`.
15. **Compartilhamento controlado** com profissionais de saúde (links read-only com escopo).
16. **Exportação LGPD** (PDF/JSON dos dados do paciente) — relevante para o público-alvo BR.
17. **Multi-idioma** — atualmente PT-BR fixo.
18. **Observabilidade**: integrar logs estruturados (mesmo via `console` + Cloudflare).
19. **Offline-first**: já há `OfflineBanner`, mas falta cache real (Service Worker / IndexedDB) para leitura.
20. **Auditoria contínua**: rotina periódica para revisar `access_logs`.
